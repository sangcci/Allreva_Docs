# RFC: Blue-Green 전환 순서 재현과 검증

> 상태: 검토 중
> 작성일: 2026-07-30
> 관련 Issue: Allreva_BE#116

## 제안 요약

현재 배포 스크립트는 새 slot의 health check가 통과하면 이전 slot을 제거하고, 이후 별도 Nginx job에서 upstream을 새 slot으로 바꾼다. 이 순서가 실제 요청 실패를 만드는지 운영과 분리된 Docker 환경에서 재현한다.

실험에서는 현재 순서와 “Nginx 전환 후 이전 slot 종료” 순서를 같은 요청 조건에서 비교한다. 결과를 확인하기 전에는 현재 배포를 무중단이라고 단정하지 않는다.

## 왜 지금 필요한가

`deploy/deploy.sh`와 Nginx 전환 job은 서로 다른 runner에서 순서대로 실행된다. 이전 slot이 Nginx upstream으로 남아 있는 동안 제거되면, 전환이 끝나기 전 요청이 실패할 가능성이 있다.

가능성만으로 배포 방식을 바꾸면 필요 이상의 복잡도를 추가할 수 있다. 반대로 실제 실패 구간이 있는데 확인하지 않으면 사용자 요청이 끊기는 배포를 계속 운영하게 된다.

## 목표

- 운영 서버를 건드리지 않고 현재 전환 순서를 재현한다.
- 두 전환 순서의 요청 실패 수와 최대 연속 실패 시간을 비교한다.
- 재현 스크립트와 원본 결과를 보존한다.

## 이번에는 하지 않는 일

- 운영 배포 스크립트 수정
- 실제 운영 트래픽 부하 테스트
- 무중단 배포 보장 또는 SLO 확정

## 선택지

### 선택지 A: 현재 순서 유지

새 slot의 health check가 통과하면 이전 slot을 종료하고, 그 뒤 Nginx upstream을 바꾼다.

- 장점: 현재 스크립트를 바꾸지 않는다.
- 단점: Nginx가 종료된 이전 slot을 가리키는 구간이 생길 수 있다.
- 영향: 요청 실패 여부를 확인하지 못한 상태가 유지된다.

### 선택지 B: Nginx 전환 후 이전 slot 종료

새 slot의 health check가 통과하면 Nginx upstream을 먼저 바꾸고, 새 slot으로 요청이 전달되는 것을 확인한 뒤 이전 slot을 종료한다.

- 장점: 이전 slot을 제거하기 전에 proxy 경로를 새 slot으로 바꾼다.
- 단점: 전환 확인과 rollback 기준을 더 명확히 정해야 한다.
- 영향: deploy job과 Nginx job의 책임 및 순서를 조정해야 한다.

## 권장안

먼저 격리된 환경에서 선택지 A와 B를 비교한다. 재현 결과에서 A가 요청 실패를 만들고 B가 같은 조건에서 이를 줄이면, B를 채택하는 ADR과 실제 배포 스크립트 변경 Issue를 만든다.

## 예상 영향과 위험

- 실험 컨테이너, 네트워크, 포트는 운영 구성과 분리한다.
- mock application을 사용하므로 실제 Spring Boot 시작 시간과 네트워크 지연을 완전히 재현하지 못한다.
- 결과는 전환 순서의 요청 경로 문제를 보여 주는 근거이며, 실제 운영 가용성을 보장하지 않는다.

## 검증 계획

- 일정 간격으로 proxy endpoint에 요청을 보낸다.
- 현재 순서에서는 이전 slot 종료와 upstream 전환 사이에 의도적인 지연을 둔다.
- 개선 순서에서는 upstream 전환 후 이전 slot을 종료한다.
- 성공·실패 요청 수와 최대 연속 실패 시간을 원본 요청 로그에서 계산한다.

## 결정이 필요한 점

- 없음. 이번 단계는 운영 변경 전 재현과 측정만 한다.
