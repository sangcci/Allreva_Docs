# Allreva Backend Code Convention

## 대 전제
- 코드가 문서가 되어야 한다. 코드만 보고도 비즈니스 로직의 이해 + 코드 컨벤션에 대해 이해할 수 있어야 한다 -> 가독성
  - 문서화는 힘들고 귀찮은 일이기 때문에 최신화를 까먹을 수 있기 때문 -> 문서화를 최소화하는 방향 지향
- 코드와 문서 내용이 일치하지 않는다면 문서를 고치자
  - 대게 문서가 잘못된 경우가 많음

## 요약

- 우리는 모놀리식 구조를 쓰지만, 모듈 경계와 의존 방향은 분명하게 가져간다.
- `domain -> application -> presentation/infra`처럼 역할이 섞이지 않게 유지한다.
- 모듈 간 협력은 기본적으로 다른 모듈의 repository/service를 직접 참조하는 방식을 허용한다.
- 다만 트랜잭션을 분리해야 하거나, 커밋 이후 처리, 비동기 후속 작업이 필요하면 event로 분리한다.
- DTO는 `*Request`, `*Response`를 기본으로 간다.
- 비즈니스 예외는 `CustomException + ErrorCode` 체계를 따른다.
- API 응답은 공통 `Response<T>` 래퍼를 사용한다.
- endpoint convention은 `requirements/API명세.md`를 우선 기준으로 본다.
- 테스트는 통합 테스트 중심으로 본다.
- 포맷은 Spotless + Palantir Java Format 기준으로 맞춘다.

---

## 1. 아키텍처 / 모듈

- 모놀리식 구조를 사용한다.
- 다만 단순히 한 덩어리로 두기보다, 모듈 경계와 의존 방향이 보이게 유지한다.
- 기본 결은 Hexagonal Architecture / Ports & Adapters에 가깝게 가져간다.

예시

```text
[ Presentation ]
        |
        v
[ Application ] <---- [ Infra ]
        |
        v
[   Domain   ]
```

이유
- 새 코드를 넣을 때 어디에 둬야 하는지 바로 판단할 수 있어야 한다.

---

## 2. 레이어 역할

### Domain
- 가장 순수한 계층이다.
- Spring, DB, 외부 API 구현체를 직접 알지 않는다.
- 엔티티, 값 객체, 도메인 규칙, 도메인 이벤트, repository interface를 둔다.

예시
- `Email`
- `RefundAccount`
- `ConcertRepository`

하지 않음
- domain에서 외부 client 호출
- domain에서 Spring Bean 의존

이유
- 도메인 규칙은 구현 기술보다 오래 살아남아야 한다.

### Application
- 유스케이스를 조합한다.
- 트랜잭션 경계를 관리한다.
- 도메인 조회, 검증, 저장, 이벤트 발행을 맡는다.
- 상세 구현 로직이 많아진다면 분류 필요 -> 조회에 갖가지 조건 혹은 비즈니스 로직이 붙는다면 묶는것을 추천

예시
- `RentService`
- `SurveyService`

하지 않음
- controller 수준 request parsing 책임까지 끌고 오기
- DB 세부 구현을 service가 직접 다루기

이유
- 서비스는 흐름을 보여줘야지, 구현 상세로 가득 차면 안 된다.

### Infra
- DB, Redis, S3, FCM, SSE, 외부 API 같은 I/O 구현을 둔다.
- domain/application이 선언한 계약을 구현한다.

예시
- `KopisConcertDataSync`
- `FcmSender`
- `*RepositoryImpl`

이유
- 비즈니스 로직이 구현 기술에 끌려다니지 않게 해야 한다.

### Presentation
- Controller, Swagger interface, request/response binding을 맡는다.
- 요청을 받아 application service를 호출하고 공통 응답으로 감싼다.

예시
- `MemberController implements MemberControllerSwagger`

이유
- 진입점은 얇고 분명해야 한다.

---

## 3. 모듈 간 협력

- 기본적으로 다른 모듈의 repository/service를 직접 참조하는 방식을 허용한다.
- 다만 후속 작업을 현재 트랜잭션과 분리해야 하거나, 커밋 이후 실행 보장이 필요하거나, 비동기 처리가 더 자연스러운 경우에는 event 기반으로 분리한다.

예시
- 검색어 집계: `KeywordSearchedEvent`
- 알림 발송: `NotificationEvent`

이유
- 모놀리식에서는 단순한 직접 호출이 더 현실적일 때가 많다.
- 대신 트랜잭션 경계가 달라지는 순간에는 event가 더 안전하다.

## 4. 네이밍

이 섹션은 가급적 취향이 아니라 규칙으로 본다. 새 이름을 지을 때는 아래 표의 어휘를 먼저 쓴다.

### 4.1 클래스명

| 대상 | 규칙 | 예시 | 하지 않음 |
|---|---|---|---|
| Controller | `*Controller` | `RentController` | `HelperController` |
| Swagger interface | `*ControllerSwagger` | `RentControllerSwagger` |  |
| Service | `*Service` | `RentService` | `CommonService`, `DataService` |
| Scheduler | `*Scheduler` | `PopularKeywordScheduler` |  |
| Repository 계약 | `*Repository` | `ConcertRepository` | `UtilRepository` |
| Repository 구현 | `*RepositoryImpl` | `RentRepositoryImpl` |  |
| 외부 연동 port | 역할 기반 suffix | `NotificationSender`, `TargetStorage`, `AuthClient` |  |
| Event | `*Event` | `NotificationEvent` |  |
| ErrorCode | `*ErrorCode` | `RentErrorCode` |  |

이유
- 클래스명만 보고 역할과 레이어가 바로 보여야 한다.

### 4.2 DTO 이름

| 대상 | 규칙 | 예시 |
|---|---|---|
| 요청 DTO | `*Request` | `RentRegisterRequest` |
| 응답 DTO | `*Response` | `MemberProfileResponse` |
| 상세 응답 | `*DetailResponse` | `ConcertDetailResponse` |
| 요약/목록 응답 | `*Summary`, `*Thumbnail` | `HostedRentSummaryResponse` |
| 식별자 요청 | `*IdRequest` | `SurveyIdRequest` |
| 페이징 목록 응답 | `SliceResponse<T>` | `Response<SliceResponse<HostedRentSummaryResponse>>` |

이유
- DTO 역할을 이름만 보고 바로 구분할 수 있어야 한다.

### 4.3 Service 메서드 어휘

| 의미 | 고정 어휘 | 예시 |
|---|---|---|
| 단건 조회 | `get*` | `getConcertDetail` |
| 목록/조건 조회 | `find*` | `findJoinSurveyList` |
| 검색 | `search*` | `searchRents` |
| 생성/등록 | `register*` | `registerRefundAccount` |
| 개설 | `open*` | `openSurvey` |
| 참여 | `join*` | `joinRent` |
| 수정 | `update*` | `updateRent` |
| 상태 표시 | `mark*` | `markNotificationAsRead` |
| 삭제 | `delete*` | `deleteSurvey` |
| 제거 | `remove*` | `removeRefundAccount` |
| 마감/종료 | `close*` | `closeRent` |
| 취소 | `cancel*` | `cancelRentJoin` |
| 검증 | `validate*` | `validateNickname` |
| 존재 여부 | `exists*` | `existsByNickname` |
| 불리언 판단 | `is*` | `isHost` |

하지 않음

| 지양 어휘 | 이유 |
|---|---|
| `process*` | 의미가 너무 넓다 |
| `handle*` | 유스케이스가 안 보인다 |
| `execute*` | 실행만 보이고 도메인 의미가 약하다 |
| `do*` | 정보가 거의 없다 |
| 의미 없이 `create/update/delete` 반복 | CRUD만 남고 맥락이 사라진다 |

이유
- 서비스 메서드가 비즈니스 흐름을 보여줘야 한다.
- 범용 동사는 코드가 커질수록 의미가 금방 흐려진다.

### 4.4 Controller 메서드

| 규칙 | 예시 |
|---|---|
| 가능하면 service 메서드명과 의미를 맞춘다 | `getConcertDetail`, `searchRents`, `registerRefundAccount`, `cancelRentJoin` |
| HTTP path와 메서드명을 같이 봤을 때 유스케이스가 드러나야 한다 | `searchRents` + `/rents/search` |

### 4.5 Endpoint 어휘

| 대상 | 규칙 | 예시 |
|---|---|---|
| resource | 복수형 명사 | `concerts`, `rents`, `surveys`, `members`, `notifications` |
| 목록 | `list` | `/surveys/list` |
| 검색 | `search` | `/concerts/search` |
| 자동완성 | `suggestions` | `/rents/suggestions` |
| 메인 노출 | `main` | `/concerts/main` |
| 내 리소스 | `me` | `/rents/me/hosted` |
| 참여 | `join`, `apply` | `/rents/join`, `/surveys/apply` |
| 인증 토큰 | `token`, `reissue` | `/auth/token/reissue` |

원칙
- 화면 이름보다 데이터 의미가 보이는 path를 우선한다.

## 5. DTO

- 요청 DTO는 `*Request`
- 응답 DTO는 `*Response`
- 요약/목록형 응답은 `*Summary`, `*Thumbnail`, `*DetailResponse`
- 식별자 요청은 `*IdRequest`
- 페이징 응답은 모듈별로 따로 만들기보다 `common.pagination.SliceResponse`를 우선 사용한다.
- slice/page 성격의 목록 응답은 `SliceResponse<T>`로 감싼다.

예시
- `RentRegisterRequest`
- `ConcertDetailResponse`
- `HostedRentSummaryResponse`
- `SurveyIdRequest`
- `Response<SliceResponse<HostedRentSummaryResponse>>`

이유
- DTO 역할을 이름만 보고 바로 구분할 수 있어야 한다.
- 페이지 응답 구조를 공통으로 가져가야 API가 모듈마다 제각각 되지 않는다.

---

## 6. 트랜잭션

- 조회는 `@Transactional(readOnly = true)`
- 쓰기는 `@Transactional`
- 메서드 단위로 명시한다

이유
- 읽기/쓰기 의도가 코드에 바로 드러나야 한다.

---

## 7. Repository / Port / Infra

- DB 영속성 계약은 보통 `domain`의 repository interface로 둔다.
- 외부 API, 외부 저장소, 검색, 알림 같은 것은 `application/port`에 둔다.
- 구현체는 `infra`에 둔다.

예시
- domain: `ConcertRepository`
- port: `NotificationSender`
- infra: `FcmSender`

이유
- 계약과 구현을 분리해두면 바꿔야 할 범위가 줄어든다.

---

## 8. API 응답

- 모든 API 응답은 공통 `Response<T>` 래퍼를 사용한다.
- 성공 응답은 `Response.onSuccess(...)`
- 실패 응답은 `Response.onFailure(...)`
- 페이징 응답은 `Response<SliceResponse<T>>` 형태를 우선 사용한다.

응답 필드
- `timeStamp`
- `code`
- `message`
- `result`

이유
- 응답 형식이 흔들리면 클라이언트와 서버 간 협업에 지장이 생긴다
- 페이지 응답도 공통 래퍼 안에서 같은 방식으로 읽혀야 한다.

---

## 9. 예외 처리

- 비즈니스 예외는 `CustomException`을 사용한다.
- 예외 코드는 `ErrorCode` enum 기반으로 관리한다.
- 공통 예외는 `GlobalErrorCode`, 도메인 예외는 `*ErrorCode`로 분리한다.
- 최종 HTTP 변환은 `CustomControllerAdvice`에서 처리한다.

예시
- `MemberErrorCode`
- `RentErrorCode`
- `SurveyErrorCode`

하지 않음
- raw runtime exception을 서비스 곳곳에서 제각각 던지기

이유
- 예외 응답 형식을 일관되게 유지해야 한다.

---

## 10. 테스트

- 통합 테스트 위주로 테스트 진행.
- `IntegrationTestSupport` 기반 패턴을 따른다.
- Testcontainers PostgreSQL / Redis, WireMock을 사용한다.
- fixture를 적극 재사용한다(Instancio 사용).
- 테스트 이름은 DCI 스타일이나 한국어 문장형처럼, 시나리오가 읽히게 쓴다.

예시
- `Describe_*`, `Context_*`, `it_*`
- `MemberFixture`, `RentFixture`

이유
- 테스트는 검증 코드이기도 하지만, 같이 읽는 문서이기도 하다.

---

## 11. Formatter / Quality Gate

- 포맷은 **Palantir Java Format** 기준으로 맞춘다.
- Spotless가 이를 강제한다.
- 수동 정렬보다 formatter 결과를 우선한다.

명령어

```bash
./gradlew spotlessApply
./gradlew spotlessCheck
```

이유
- 포맷으로 사람 취향이 섞이기 시작하면 리뷰 비용만 늘어난다.
