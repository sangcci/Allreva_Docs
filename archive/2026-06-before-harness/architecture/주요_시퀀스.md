# OAuth2 로그인 프로세스

- 모듈 분리: auth 모듈은 member 모듈의 서비스가 아닌 Repository에만 의존하거나, 혹은 MemberService의 특정 '조회' 기능에만 의존하도록 결합도를 낮추세요.
- DTO 일관성: UserInfoResponse처럼 모든 정보를 한 번에 주는 구조도 좋지만, "인증 도메인"과 "회원 도메인"의 정보를 분리하여 필요한 것만 내려주는 AuthContext 객체를 내부에 도입하는 것을 추천합니다.



```mermaid
sequenceDiagram
     autonumber
     participant U as 사용자 (User)
     participant Auth as WAS
     participant External as OAuth2 외부 API
     participant Member as RDB
     participant Cred as Redis

     Note over U, External: [1단계: 신원 확인 (Identity Verification)]
     U->>Auth: 로그인 요청 (Credential/Code)
     Auth->>External: 신원 검증 및 프로필 요청
     External-->>Auth: 검증된 신원 정보 (Verified Identity)

     Note over Auth, Member: [2단계: 계정 맵핑 (Identity Mapping)]
     Auth->>Member: 기존 회원 식별 (Provider ID / Email)

     alt 신규 식별자 (First-time Login)
         Member-->>Auth: 회원 정보 없음
         Auth-->>U: 가입 대기 상태 응답 (Temporary Identity)
         Note right of U: User completes profile signup
     else 기존 회원 (Existing Member)
         Member-->>Auth: 로컬 회원 식별 성공 (Member ID)

         Note over Auth, Cred: [3단계: 권한 부여 및 세션 발행 (Issue Credentials)]
         Auth->>Auth: 내부 보안 토큰 생성 (JWT Access/Refresh)
         Auth->>Cred: 세션/리프레시 토큰 영속화 (Rotation 정책 적용)

         Note over Auth, U: [4단계: 결과 반환 (Response Delivery)]
         Auth-->>U: 인증 완료 (Access Token: Header / Refresh Token: Cookie)
end
```

# 공연 및 공연장 데이터 배치 업데이트 프로세스

고려할 점

- Bulk Insert 고려: 데이터 양이 방대할 경우 건당 save보다는 saveAll을 통해 배치를 묶어서 DB에 던지는 방식(Bulk Insert)으로 성능을 더 높일 수 있습니다.
- Circuit Breaker: KOPIS partial failure(타임아웃 반복) 시 스케줄러 스레드가 수 시간 점유되는 상황을 조기 차단하는 용도. 단, 스케줄러는 전용 스레드 풀을 사용하므로 사용자 API 스레드로의 직접 전파 위험은 낮음. 또한 현재 구조는 메서드 단위 @Transactional 없이 repository 메서드별 개별 트랜잭션으로 동작하므로, KOPIS 타임아웃 대기 중 DB 커넥션을 점유하지 않아 커넥션 풀 고갈 위험도 낮음.
- 장애 복구 전략 (Rollback vs Checkpoint): hall 간 의존성이 없는 독립 작업이므로 롤백보다 재시작 지점 기록(Checkpoint)이 적합한 구조. Spring Batch의 JobExecutionContext가 이를 지원하나, 일 1회 전체 재순회로 자연스럽게 재처리되는 구조이므로 단순 스케줄러로 충분하다고 판단. (실패한 hall은 다음날 새벽 4시에 자동 재처리됨)
- Spring Batch 미도입 근거: Checkpoint/Restart, 대용량 Chunk 처리, Job 실행 이력 관리 세 가지 중 해당 없음. 프로젝트 내 Spring Batch를 사용하는 곳이 있더라도 도구는 문제에 맞게 선택해야 하며, 억지로 도입하면 코드 복잡도만 증가 (Job/Step/Reader/Processor/Writer + JobRepository 메타 테이블).

## 공연장 동기화 (매월 1일 새벽 2시)

```mermaid
sequenceDiagram
    autonumber
    participant Scheduler as ConcertHallSyncScheduler
    participant Cache as Cache Layer (Caffeine)
    participant KOPIS as KOPIS API
    participant DB as RDB (concert_hall)

    Scheduler->>Cache: @CacheEvict("placeMain") — 전체 캐시 무효화
    Scheduler->>DB: findAllFacilityCodes() — DB에 등록된 시설 코드 전체 로드
    Note right of DB: hall_code에서 접두어(FC000001) 추출, 약 434개

    loop 각 facilityCode별 순회
        Scheduler->>KOPIS: 공연장 상세 조회 (facilityCode)
        KOPIS-->>Scheduler: 해당 시설의 공연장 목록 (XML)
        Scheduler->>DB: findHallCodesByFacilityCode() — 화이트리스트 조회
        Note right of Scheduler: DB에 존재하는 hallCode만 UPSERT (신규 공연장 자동 추가 방지)
        loop 응답 내 각 hall
            alt hallCode가 화이트리스트에 존재
                Scheduler->>DB: save(hall) — 공연장 정보 갱신
            else 미등록 hallCode
                Scheduler->>Scheduler: skip (log)
            end
        end
        Note right of Scheduler: 100ms sleep (KOPIS rate limit 준수)
    end
```

## 공연 정보 동기화 (매일 새벽 4시)

```mermaid
sequenceDiagram
    autonumber
    participant Scheduler as ConcertSyncScheduler
    participant KOPIS as KOPIS API
    participant DB as RDB (concert)

    Scheduler->>DB: findAllHallCodes() — 공연장 코드 전체 로드 (약 831개)
    Scheduler->>DB: findAll() — 전체 공연 로드 → concertCode:status Map 구성
    Note right of DB: 이후 status 비교에서 DB 조회 없이 메모리 Map 사용

    loop 각 hallCode별 순회 (약 831회)
        Scheduler->>KOPIS: 당월 공연 목록 조회 (hallCode, startDate, endDate, today)
        KOPIS-->>Scheduler: 공연 코드 + 현재 상태(prfstate) 목록 (XML)
        Note right of Scheduler: 100ms sleep (hall 단위 rate limit)

        loop 응답 내 각 ConcertSummary
            alt 기존 공연이 COMPLETED 상태
                Scheduler->>Scheduler: skip — 종료 공연은 갱신 불필요
            else status 변경 없음 (existing == summary.status)
                Scheduler->>Scheduler: skip — 변경분 없으면 API 호출 안 함
            else 신규 공연 or status 변경됨
                Scheduler->>KOPIS: 공연 상세 조회 (hallCode, concertCode)
                KOPIS-->>Scheduler: 공연 상세 정보 (XML)
                Scheduler->>DB: findById(concertCode) — 기존 여부 확인
                alt 기존 공연
                    Scheduler->>DB: updateFrom(fetched) + save() — 정보 갱신
                else 신규 공연
                    Scheduler->>DB: save(fetched) — 신규 저장
                end
                Note right of Scheduler: 100ms sleep (detail 호출마다 rate limit)
            end
        end
    end
```

실측 기준 (2026-05-04 로컬 실행):
- 공연장 동기화: 약 142초 (facilityCode 434개 × HTTP + 100ms sleep)
- 공연 정보 동기화: 약 310초 (hallCode 831개 × summary HTTP + 100ms sleep, 상세 API 92회 추가 호출)

# 아티스트 데이터 조회 프로세스

```mermaid
sequenceDiagram
     autonumber
     participant U as Client (User)
     participant API as Artist API (Service)
     participant Adapter as External Adapter (Spotify)
     participant ExtAuth as Ext-Auth Provider    
     participant ExtAPI as Ext-Data Provider
     participant DB as Local Store (RDB)
    
     Note over U, API: [1단계: 실시간 검색 (Live Search)]
     U->>API: 아티스트 검색 요청 (Query)

     Note over API, ExtAuth: [2단계: 외부 인증 및 접근 권한 확보]
     API->>Adapter: 데이터 요청
     Adapter->>ExtAuth: API Access Token 요청 (Client Credentials)
     ExtAuth-->>Adapter: 유효한 Token 반환

     Note over Adapter, ExtAPI: [3단계: 외부 데이터 수집 및 변환]
     Adapter->>ExtAPI: 아티스트 정보 조회 (With Token)
     ExtAPI-->>Adapter: Raw Data 반환 (JSON)
     Adapter->>Adapter: 외부 스키마 -> 내부 DTO 변환 (Mapping)
     Adapter-->>API: 정제된 아티스트 목록 반환
     API-->>U: 검색 결과 응답

     Note over U, DB: [4단계: 온디맨드 동기화 (Just-in-Time Sync)]
     U->>API: 특정 아티스트 기반 액션 (예: 공연 등록)
     API->>DB: 로컬 존재 여부 확인
     alt 데이터가 없는 경우
         API->>DB: 아티스트 기본 정보 저장 (ID, Name)
         Note right of DB: 참조 무결성을 위해 최소 정보만 동기화
     end
     API-->>U: 액션 완료 (Linked)

```

- Token Caching: 외부 API Access Token은 만료 전까지 유효하므로, 매번 발급받지 않고 Redis에 캐싱하여 성능을 높이는 설계를 언급하면 좋습니다.
- Rate Limiting 처리: 외부 API는 호출 횟수 제한이 있는 경우가 많습니다. 이를 대비해 Resilience4j 같은 라이브러리로 Rate Limiter를 적용하는 고민을 했다고 하면 더욱 전문적으로 보입니다.
- Lazy Loading vs Eager Loading: 아티스트의 상세 이미지나 앨범 정보는 검색 시점이 아닌, 상세 조회 시점에 가져오도록 설계하여 응답 속도를 관리합니다.
