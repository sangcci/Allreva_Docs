# Issue 작성과 분류 기준

Issue는 작업을 시작하기 전에 문제와 완료 조건을 맞추는 곳이다. 구현 방법을 길게 적는 설계 문서가 아니다. 설계 선택지가 크면 RFC를 먼저 만들고 Issue에서 링크한다.

## Issue 종류

| 종류 | 언제 쓰는가 | 자동 라벨 |
| --- | --- | --- |
| 기능 또는 개선 | 사용자 기능이나 기존 동작을 바꿀 때 | `✨ feat` |
| 버그 리포트 | 기대한 결과와 실제 결과가 다를 때 | `🐛 bug` |
| 공통 개발 작업 | 리팩터링, 테스트, 문서, CI/CD, 운영 정리 | 선택한 작업 유형에 따라 자동 부착 |

공통 개발 작업에서는 `REFACTOR`, `TEST`, `DOCS`, `CI`, `CHORE`, `PERF` 중 하나를 고른다. 제목 접두사도 같은 유형으로 직접 맞춘다. 예를 들어 테스트 작업은 `[TEST] 로그인 회귀 테스트 보강`처럼 쓴다.

## 모든 Issue에 필요한 정보

- 왜 지금 이 작업이 필요한지
- 이번 작업의 범위
- 닫기 전에 확인할 수 있는 완료 조건

기능과 공통 개발 작업의 구현 메모는 선택 항목이다. 아직 방법을 정하지 못했거나 선택지가 크면 Issue에서 결론을 내리려 하지 말고 RFC를 만든다.

## 완료 조건을 쓰는 방법

완료 조건은 작업 목록이 아니라 결과를 확인하는 기준이다.

```text
나쁨: Service를 수정한다.
좋음: 온보딩 완료 여부가 로그인 응답에 반환되고, 관련 통합 테스트가 통과한다.
```

작은 문서 수정처럼 단순한 작업도 한 줄이면 충분하다. 예를 들어 “README의 실행 명령이 현재 프로젝트와 일치한다”처럼 쓴다.

## 중요한 변경의 문서 연결

아키텍처, API 계약, DB 스키마, CI/CD·운영 방식, 사용자 흐름을 바꾸는 Issue는 Allreva_Docs의 RFC, ADR 또는 관련 문서 링크를 남긴다. 단순 버그 수정이나 테스트 보강은 문서 링크가 꼭 필요하지 않다.
