# Issue 작성과 분류 기준

Issue는 Research, 사용자와의 대화, 승인된 plan 뒤 개발 workflow에 진입하기 전에 문제, 범위, 완료 조건을 맞추는 곳이다. 구현 방법을 길게 적는 설계 문서가 아니다.

## Issue 종류

| 종류 | 언제 쓰는가 | 자동 라벨 |
| --- | --- | --- |
| 문서 작업 | 문서 추가, 정리, 구조 변경이 필요할 때 | `📝 docs` |
| 문서 오류 | 잘못된 설명, 깨진 링크, 오래된 안내를 고칠 때 | `🐛 bug` |

Issue Form이 두 라벨 중 하나를 자동으로 붙인다. 제목도 같은 종류로 시작한다. 문서 작업은 `[DOCS]`, 문서 오류는 `[BUG]`를 사용한다.

## 모든 Issue에 필요한 정보

- 왜 지금 이 작업이 필요한지
- 이번 작업의 범위
- 닫기 전에 확인할 수 있는 완료 조건

구현 또는 작성 메모는 선택 항목이다. 승인된 plan의 핵심과 완료 조건을 짧게 적는다.

## 완료 조건을 쓰는 방법

완료 조건은 작업 목록이 아니라 결과를 확인하는 기준이다.

```text
나쁨: Service를 수정한다.
좋음: 온보딩 완료 여부가 로그인 응답에 반환되고, 관련 통합 테스트가 통과한다.
```

작은 문서 수정처럼 단순한 작업도 한 줄이면 충분하다. 예를 들어 “README의 실행 명령이 현재 프로젝트와 일치한다”처럼 쓴다.

## 중요한 결정의 문서 연결

여러 작업에 오래 영향을 주는 중요한 아키텍처, 운영 또는 정책 결정을 확정하면 ADR 링크를 남긴다. 단순 버그 수정, 테스트 보강, 단일 선택지 문서 수정은 ADR이 필요하지 않다.
